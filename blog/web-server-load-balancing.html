Web Server Load Balancing Lab

23 Oktober 2026 • Project 09 / 15

Pendahuluan

Setelah beberapa lab sebelumnya berfokus pada jaringan dan server tunggal, kali ini saya ingin naik satu lapis: bagaimana sebuah layanan web bisa dilayani oleh lebih dari satu server. Di lab ini saya membangun satu load balancer dengan dua backend, yang saya sebut Server A dan Server B, lalu mengamati bagaimana request dibagikan di antara keduanya.

Alasan saya membuat lab ini cukup sederhana. Selama ini saya hanya mengenal satu server untuk satu layanan, dan saya penasaran bagaimana situs yang ramai tetap bisa diakses ketika salah satu servernya bermasalah. Jawabannya ternyata bukan sekadar menambah server, tetapi ada komponen di depan yang menentukan request mana pergi ke mana. Load balancer inilah yang ingin saya pahami secara langsung, bukan hanya dari teori.

Lab ini juga menjadi lanjutan yang masuk akal dari pembelajaran server dan virtualisasi sebelumnya. Karena sudah terbiasa menjalankan beberapa server virtual, saya bisa fokus pada sisi distribusi trafiknya tanpa perlu pusing lagi soal cara menyiapkan servernya. Seluruh pengujian saya lakukan dalam skala lab untuk belajar, bukan untuk kebutuhan operasional nyata.

Tujuan

  • Memahami bagaimana load balancer mendistribusikan request ke dua backend server.
  • Membandingkan perilaku metode Round Robin, Least Connections, dan IP Hash melalui pengujian langsung.
  • Mengenal session persistence dan hubungannya dengan metode distribusi yang dipilih.
  • Mengamati perilaku sistem ketika salah satu backend tidak tersedia, serta berlatih troubleshooting backend.

Tools / Perangkat

  • Satu load balancer dan dua backend server (Server A dan Server B).
  • HTTP sebagai protokol yang diuji.
  • curl untuk mengirim request berulang ke load balancer.
  • Identitas backend pada response, untuk melihat server mana yang menangani request.
  • Pengecekan status server dan log request saat troubleshooting.

Proses yang Dilakukan

  1. Menyiapkan Server A dan Server B agar masing-masing dapat melayani request HTTP dan bisa dibedakan dari response-nya.
  2. Menempatkan load balancer di depan kedua backend, sehingga request diarahkan ke satu alamat load balancer.
  3. Mengirim request berulang menggunakan curl dan mencatat backend mana yang merespons.
  4. Menguji metode Round Robin, lalu mengamati pola giliran antar backend.
  5. Beralih ke Least Connections dan mengamati pengaruh jumlah koneksi aktif terhadap distribusi.
  6. Menguji IP Hash dan mengamati konsistensi backend untuk klien yang sama.
  7. Mematikan salah satu backend, lalu mengamati apakah load balancer tetap melayani request melalui backend yang tersisa.

Bagian yang paling banyak menyita waktu justru pengujian dengan curl. Setiap request saya kirim ke alamat load balancer, lalu saya lihat identitas backend pada response-nya. Dari puluhan request berturut-turut, pola distribusi mulai terlihat: pada Round Robin, response bergantian antara Server A dan Server B secara teratur. Saya mengulang pengujian yang sama setelah metode diganti, supaya perbedaannya benar-benar berasal dari metode, bukan dari kebetulan.

Perbedaan antar metode menjadi lebih jelas ketika saya bandingkan catatannya. Round Robin membagi secara bergiliran tanpa peduli beban. Least Connections memilih backend dengan koneksi aktif paling sedikit, sehingga distribusinya bisa terlihat tidak merata ketika jumlah koneksi tiap server berbeda. IP Hash berperilaku lain lagi: klien dengan alamat IP yang sama terus diarahkan ke backend yang sama. Di sinilah saya pertama kali melihat session persistence bekerja secara nyata, bukan sebagai istilah di dokumentasi.

Pengujian terakhir adalah mematikan salah satu backend. Saya ingin memastikan bahwa request tetap dilayani, dan bahwa load balancer benar-benar berhenti mengirim request ke backend yang mati. Verifikasi saya lakukan dengan melihat response yang masuk dan mengecek status server secara manual, bukan dengan berasumsi trafiknya otomatis pindah.

Kendala / Hal yang Diperhatikan

Hal pertama yang perlu diperhatikan adalah jumlah request saat pengujian. Dengan hanya beberapa request, pola distribusi belum tentu terlihat, dan saya bisa salah menyimpulkan bahwa suatu metode tidak bekerja. Selain itu, karena curl saya jalankan dari alamat IP yang sama, pengujian IP Hash selalu menghasilkan backend yang sama. Sekilas ini terlihat seperti load balancer tidak membagi trafik, padahal justru itulah perilaku yang diharapkan dari IP Hash. Membedakan konfigurasi yang salah dari metode yang memang bekerja seperti itu ternyata butuh catatan pengujian yang rapi.

Hal kedua adalah ketersediaan backend. Ketika salah satu server dimatikan, saya perlu memeriksa apakah load balancer mendeteksinya dan berhenti mengarahkan request ke sana. Pengecekan log request dan status server menjadi penting, karena kegagalan backend tidak selalu terlihat dari sisi klien selama backend lain masih merespons. Dari sini saya belajar bahwa troubleshooting load balancing bukan hanya soal konfigurasi load balancer, tetapi juga soal memastikan kondisi tiap backend secara terpisah.

Hasil dan Pemahaman

Dari pengujian yang saya lakukan, ketiga metode menunjukkan perilaku yang berbeda sesuai konsepnya. Round Robin menghasilkan giliran yang teratur antara Server A dan Server B. Least Connections membuat distribusi mengikuti jumlah koneksi aktif, sehingga tidak selalu bergantian secara kaku. IP Hash menjaga klien yang sama tetap berada di backend yang sama, yang saya pahami sebagai bentuk session persistence.

Ketika salah satu backend dimatikan, request tetap dapat dilayani oleh backend yang masih aktif, selama load balancer tidak lagi mengarahkan request ke backend yang mati. Pengujian ini berhasil menunjukkan perilaku dasar yang saya harapkan, meskipun saya menyadarinya hanya pada skala lab dengan dua backend dan pengujian curl sederhana.

Pemahaman terbesar yang saya dapat: metode distribusi menentukan karakter sistem. Tidak ada metode yang selalu paling benar; Round Robin cocok untuk beban yang mirip, Least Connections mempertimbangkan kondisi koneksi, dan IP Hash menjaga sesi tetap konsisten. Saya juga memahami bahwa load balancer hanya sebagus informasi yang dimilikinya tentang backend, sehingga pengecekan ketersediaan backend adalah bagian dari desain, bukan tambahan.

Load balancing bukan hanya soal membagi request, tetapi memahami bagaimana setiap koneksi diarahkan dan bagaimana sistem bereaksi ketika backend berubah.

Hal yang Dipelajari

  • Load balancer berada di antara klien dan backend, dan memutuskan ke mana setiap request diarahkan.
  • Round Robin, Least Connections, dan IP Hash memiliki dasar keputusan yang berbeda: giliran, beban koneksi, dan identitas klien.
  • Session persistence berkaitan erat dengan pilihan metode distribusi.
  • Ketersediaan backend perlu diverifikasi, bukan diasumsikan, terutama saat salah satu backend mati.
  • curl dan identitas backend pada response adalah cara sederhana namun efektif untuk menguji distribusi request.

Kesimpulan

Lab ini adalah langkah pertama saya dari mindset satu server menuju beberapa server yang bekerja bersama. Saya tidak hanya mempelajari cara memasang load balancer, tetapi juga cara menguji dan membaca perilakunya. Pengujian kecil dengan curl ternyata cukup untuk membuat perbedaan antar metode terlihat jelas, asalkan dilakukan dengan sabar dan dicatat.

Pengalaman ini juga menyiapkan saya untuk pembelajaran berikutnya tentang pembagian trafik di lapisan jaringan. Jika di sini yang dibagi adalah request HTTP, di lab berikutnya saya mulai mempelajari bagaimana koneksi jaringan itu sendiri yang dibagi antar jalur internet.
